Component catalogue

Reviewed 2026-10-16: Web Awesome reference catalogue. 90 reference entries and 11 existing UI primitives.

Scope mapping, not feature parity. native means a platform recipe; foundation means an existing UI primitive or adapter; planned means unimplemented. No entry is a certified accessibility claim. Proposed names may change.

Delivery phases and the stable-release gate are in ROADMAP.md. Examples are minimal structures, not complete applications. Native/foundation entries still need the listed release evidence. Proposed widgets have contracts instead of pretend live demos.

Existing UI primitives

ui-stack

Foundation · CSS-only. Vertical rhythm for direct children. Default geometry follows comfortable/compact data-density scopes; local component overrides still win. See docs/density.md.

<ui-stack><h2>Projects</h2><p>Your current work.</p></ui-stack>

Current API

ui-cluster

Foundation · CSS-only. Wrapping row of native controls or content. Default geometry follows comfortable/compact data-density scopes; local component overrides still win. See docs/density.md.

<ui-cluster><button type="button">Save</button><a href="/projects">Cancel</a></ui-cluster>

Current API

ui-form

Foundation · Optional JS. Wrap exactly one native form; coordinate validation and recovery. Adopt visible server field errors without moving focus. Observe native external/dynamic ownership; support grouped feedback and application-supplied prefixes/message translations. Async transport remains application-owned; see docs/forms.md.

<ui-form><form action="/projects" method="post"><label for="title">Title</label><input id="title" name="title" required><button>Save</button></form></ui-form>

Actions

Button

Native recipe · Phase 1. UI route: button; a[href].

Use buttons for actions and anchors for navigation; preserve submit, disabled, and accessible names. Native buttons support data-variant primary/secondary/quiet/danger and data-size small/default/large; anchors keep link styling.

Acceptance work: Enter/Space, focus, submitter, loading feedback, and disabled behavior.

<button type="submit">Save project</button>
<button type="reset" data-variant="secondary">Reset answers</button>
<button type="button" data-variant="quiet" data-size="small">Clear filters</button>
<a href="/projects">View projects</a>

Dialog

Native recipe · Phase 1. UI route: dialog with showModal().

Use an accessible title, explicit close action and browser modal behavior. Application code opens it, clears stale results and retains inline information when enhancement is unavailable. Long structured content starts with heading focus and scrolls as one native surface. See docs/dialog.md and its long-briefing recipe. Standard setup is available through js/ui.js and explicit data-ui markup; see docs/enhancement.md.

Acceptance work: Browser assertions cover short/long modal focus, scroll bounds, both close actions, reopening at the start, background focus blocking, close results, return focus after trigger changes and unsupported/open-failure/no-script fallback. Verify remaining browser/mobile, zoom, forced colors, touch and screen-reader combinations before release; see dated manual evidence in ACCESSIBILITY.md.

<button id="open-information" type="button" hidden>Open information</button>
<section id="information-fallback"><h2>Project information</h2><p>Keep equivalent information available before enhancement.</p></section>
<dialog id="information" aria-labelledby="information-title" hidden>
  <h2 id="information-title">Project information</h2>
  <p>Keep equivalent information available before enhancement.</p>
  <form method="dialog"><button type="submit" value="close" autofocus>Close information</button></form>
</dialog>
